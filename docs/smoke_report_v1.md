## 1. 机制验证：能否 teacher-force 真实 B 音频为模型自身输出？（你问的第 1、2 点）

**能。且这正是官方 voice prompt 的既有机制**，非我们的发明：

- 源码定位（`moshi/moshi/models/lm.py`）：
  - `prepare_step_input()` L761-779：`moshi_tokens` 参数把音频 token 逐帧写进**模型自身流的 cache 槽位**并标记 `provided=True`（用户流走 `input_tokens` 参数，两者独立）；
  - `process_transformer_output()` L892/L908-912：`provided` 位置用喂入值**强制**替代采样值——即"模型以为这句话是自己说的/正在说"；
  - `_step_voice_prompt_frame()` L1015-1019：官方用法 = `moshi_tokens=提示音频, input_tokens=sine 占位, text=PAD`。voice prompt 阶段就是这么干的。
- 实测（`probe_forcing.txt`，真实 B 音频编码后喂入）：
  - SINE 测试音被喂入后，**恰好 1 帧（=max_delay）**后出现在模型输出流；
  - 真实 B 音频抽样 4 帧（feed 60/65/70/79）→ **输出逐 token 逐位匹配**；
  - 文本流强制 PAD 期间模型输出文本恒为 PAD(3)。

**边界说明（如实报告）**：官方演练过的组合只有「moshi 流被强制 + 用户流填 sine」。我们的 `interleave` 模式额外把**历史 A 音频**喂进用户流——使用的是公开 `step()` 参数、未修改模型，但属于官方未演练的组合（官方 live 阶段只喂"当前"用户音频，没有回放历史用户音频的路径）。为保守起见 harness 同时实现了：

- `official` 模式：仅 B 历史做 voice-prompt 式回放（用户流全程 sine）——严格贴合官方既有机制；
- `interleave` 模式：双轨回放（B→moshi 流、A→用户流、重叠时同时）——上下文更完整，但属 API 级延伸。

两模式均端到端跑通、无报错。

## 2. 冒烟运行与真实输出（你问的第 3、4 点）

事件来源：`selection_50.csv` 中 **A 说话人**的 pause 与 filler（PP 扮演 B，测对 A 犹豫的反应）。历史窗 45s。

| case | 事件 | PP onset（RMS 判据） | 真人 B 参考 | PP 输出文本（前段） | 产物 |
|---|---|---|---|---|---|
| pause_official | A 中途停顿 1.2s（含自我修正场景） | **事件后 +6.20s** | +4.70s | "Yeah, I can hear a voice, yeah, yeah, it's okay…" | 16.2s wav |
| pause_interleave | 同上 | **+6.04s** | +4.70s | "I don't know if I have…" | 16.2s wav |
| filler_interleave | A 的 "uh"（"he's, uh, doing a very…"） | **+3.00s** | +3.61s | "Yeah, I guess the other thing…" | 15.1s wav |

- **复现性**：同一条 case 两次独立运行，onset 与文本**逐字一致**（seed_all 生效）。
- **时间粒度（你的第 4 点）**：mimi 帧率 = **12.5 Hz = 80ms 精确一致**（frame_size=1920@24kHz）；输出管线延迟 = `max_delay` = **1 帧（80ms）**，已在时间映射中校正（实测验证）；文本 token 领先可听 onset ≤1 帧。**onset 时间分辨率为 80ms**，对秒级/百毫秒级 turn-taking 测量足够。
- 逐帧记录齐全：`case_*/{tag}_frames.csv`（每帧：clip 时间 / A、B 活动 / 文本 token / 8 个音频 token / 静音判定 / 解码 RMS）、`{tag}_out.wav`（模型输出音频）、`preview.wav`（裁剪窗立体声预览，左 A 右 B，供人耳听检）。

## 3. 发现的问题清单（"上下文回放不一致"）

| # | 问题 | 性质 | 状态 |
|---|---|---|---|
| 1 | **缺 `torch.no_grad()`**：mimi 编码每帧保留 ~4.2MB 自编码图 → **3.2GB/段显存泄漏**（此前 case2 OOM 的根因） | harness bug（官方脚本均在 no_grad 下运行，我们漏了） | ✅ 已修，显存全程稳定 ~19G |
| 2 | **token 静音判据失效**：自由生成时的"静音"帧 token 与 `SILENCE_TOKENS` **仅 2/8 码本相同**（解码能量 -73dB 确为静音）→ 用 token 判据会得出"模型在回放→自由切换瞬间抢话"的**假象** | 判据错误 | ✅ 改用解码 RMS 判据（底噪+20dB、连续 3 帧、跳过首帧瞬态）。修正后：**无边界爆发**——模型在切换后静音了 6.2s / 3.0s 才开口 |
| 3 | **转写词边界 vs 声学边界抖动 ~±140ms**（pause 案例：词起点 329.1s vs 声学恢复 328.96s） | 数据特性（机器转写） | ⚠️ 标签有效（声学剖面确认真实静音 ~1.0s），正式实验建议声学修正边界 |
| 4 | **协议敏感性**：official vs interleave 输出**内容不同**（onset 相近，Δ0.16s） | 实验设计点 | ⚠️ 需你决策：固定一种 / 作为消融维度 |
| 5 | 首帧解码瞬态（-59.9dB 小尖峰） | 细节 | ✅ 判据已跳过第 0 帧 |
| 6 | 观察到有意义的对照信号：pause 案中真人 B 提前 **1.6s** 大重叠插话；PP 在 A 结束前 **0.16s** 微重叠 | 发现 | 保留为后续"重叠时长分布"指标 |

## 5. 真人 B 参考的使用（你的第 6 点）

真人 B 的 onset 在表格中**单列为参考**，不作唯一答案：本批 3 例中 PP 分别比真人**慢 1.5s / 慢 1.3s / 快 0.6s**——真人行为本身方差大（受话题、关系、说话人习惯影响），后续以**分布对比**（PP vs 真人 onset 分布、重叠时长分布）而非单点对错来评价。

## 6. 扩展到 50×3 之前需要的决策/动作

1. **协议模式拍板**（必须）：建议主实验用 `interleave`（上下文完整），`official` 作为机制保守性消融（或在子集上验证两者结论不冲突）；
2. 采用 RMS onset + 声学边界修正（脚本已就位）；
3. 你人工听检 3 个 `preview.wav` + `out.wav`；
4. （可选）把"无历史基线"加入矩阵。
5. 成本预估：50 事件 × 3 种子 × 1 模式 = 150 runs，单进程约 **3.5–4 小时** GPU 时间，显存稳定；建议先扩到 **10 事件 × 10 分钟**看分布合理性再全量。
